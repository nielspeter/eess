**Breaking (@nielspeter/eess-md):** `links()` examines every link either reading of a line-1 `---` block holds (bugs 0572, 0610, 0611, 0612; spike 0613). eess-md reads the block either as front matter, as GitHub and VitePress render it, or as Markdown, and examined only that reading's links, so a broken link the other reader follows passed: a body reference whose definition sits in the block, a body definition behind a block one of the same label, an `<a href>` in a YAML value, and a body link a fence, comment or `<pre>` opened in a YAML value would swallow. `links()` now adds the internal links only the other reading holds, and the HTML links either reading cannot read, each marked with `onlyWhere` (`'markdown'` or `'front-matter'`, a new optional `MdLinkRef` field), and a `resolve()` finding about one ends "— a link only where the line-1 `---` block is read as Markdown" (or "is front matter"). `links().select()` refuses when it reaches a link only one reading holds, naming it, so a `correspondence()` is never built on one reader's links alone. Ordinary front matter adds nothing (a URL in a YAML value is metadata, not a link); across 2,177 Markdown files measured, only test fixtures hold such a link. The document's structure (sections, title, fields, boxes) is unchanged, and so are `sections().haveLink()` and `beLinkedBack()`'s evidence, which read the reading the structure came from. A rule over links can newly go red, and its `examined` count can grow.
