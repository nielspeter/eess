**Breaking (@nielspeter/eess-md):** a link only one reading of a line-1 `---` block holds is reported (bugs 0572, 0610, 0611, 0612; spike 0613). eess-md reads the block either as front matter, as GitHub and VitePress render it, or as Markdown, and examined only that reading's links, so a broken link the other reader follows passed: a body reference whose definition sits in the block, a body definition behind a block one of the same label, an `<a href>` in a YAML value, and a body link a fence, comment or `<pre>` opened in a YAML value would swallow. Each internal link only the other reading holds is now an unsuppressable `md/link-one-reading-holds` finding (exported as `ONE_READING_LINK`) on every `links()` rule whose predicates reach it, naming the link and which reading holds it; it is not an element, so no condition or `correspondence()` can pass on it, and `links().select()` refuses when it reaches one. An HTML link the other reading cannot read is `md/unread-link`. Ordinary front matter adds nothing (a URL in a YAML value is metadata); across 2,177 Markdown files measured, only test fixtures hold such a link. A link in that position is reported even where it resolves, since the two readers disagree whether it is there; each finding names its remedy (move the link or its definition out of the block, remove one of two definitions of a label, or close in the block what it opens), and each is measured to clear it. An unquoted `<a href=…/…>` in an otherwise valid YAML value is now an unread-link finding; quoting the value clears it for an external `href`, and an internal one then needs moving out of the block. The document's structure is unchanged.
