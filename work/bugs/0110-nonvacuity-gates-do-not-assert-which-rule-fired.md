# Bug 0110: five non-vacuity gates prove a fixture ran but not which rule fired — `ruleNote` is displayed, never asserted

## Status

- **State:** Draft — confirmed against the source; the failure is demonstrable
  today for `corpus/adr` (see [0109](./fixed/0109-nonvacuity-fixtures-read-a-crash-as-a-pass.md),
  where two instances of it were fixed). No red test written yet.
- **Severity:** Medium — a missing capability plus an honesty gap: each gate
  prints a rule name it never checks. It cannot hide a violation, but it can let
  a named rule be deleted without the gate noticing.
- **Origin:** self-found · four-persona review of 0109's fix, which found the
  same class three more times
- **Reported:** 2026-08-12

## Symptom

`gateNode` takes a `ruleNote` and never asserts it:

```js
function gateNode(script, ruleNote) {
  …
  return { ok: r.code === 1, code: r.code, detail: `exit ${r.code} (${ruleNote})` }
}
```

The harness then prints five lines of the form
`corpus/links — OK (fails on violating input) · exit 1 (links resolve check)`,
each naming a rule that nothing verified. 0109 fixed exactly this for
`gateDiagram` — which matched `/violation/i` while its label claimed
`diagram/kernel-stereotype` — and for two fixtures that could announce the wrong
failure. The generalisation stopped there.

## Root cause

Proving a gate **ran** and proving the **right rule fired** are two different
assertions, and 0109 generalised only the first. Where a fixture drives a preset
that bundles several checks, "it threw" or "it exited 1" is satisfied by any of
them:

| Fixture                  | Preset behind it                                       | Bundles                                         |
| ------------------------ | ------------------------------------------------------ | ----------------------------------------------- |
| `bad-gherkin-ts.mjs`     | `scenarioTestsResolve`                                 | three citation modes                            |
| `bad-links.mjs`          | `links().should().resolve()` — built by the fixture    | one (safe by construction)                      |
| `bad-pointers.mjs`       | `pointers().should().resolve()` — built by the fixture | one (safe by construction)                      |
| `bad-review-harness.mjs` | `check-review-harness.mjs`                             | four checks; asserts one phrase, so partly safe |
| `bad-numbers.mjs`        | `next-number --check`                                  | one                                             |

`bad-links` and `bad-pointers` are safe because the fixture constructs the very
rule it tests — there is nothing else that could fire. The risk is concentrated
in the preset-driven fixtures, which is where 0109 already found two live
instances.

Two more shapes of the same gap:

- **Conjoined substrings.** `gateArch` and `gateBaseline` assert two substrings
  anywhere in the combined output (`__nonvacuity_probe__` **and** the rule), not
  that one violation has both. An unrelated violation of the same rule elsewhere
  in the repo satisfies the pair. `gateArch` already requests `--format json`;
  the blocker to parsing it is `sh()`, which concatenates stdout and stderr into
  one string.
- **Assertion on rendered prose.** `gateBaseline` matches `call to 'eval'` — a
  rule _description_ generated by the DSL — because `scripts/check-baseline.mjs`
  accepts no `--format` flag. Reword the description renderer and this gate goes
  red for a non-reason. The file already imports `reportViolations` and already
  runs `report: 'return'`, so a `--format json` passthrough is small.

## Why it matters

The gates that name a rule are the ones a reader trusts most: the line says
`adr/valid-tiers` fired. When it did not, the harness has done the thing it
exists to prevent one level up — and the person reading it has no way to tell,
because the claim and the evidence are printed on the same line.

The concrete break class: delete the rule a gate names, and the gate stays green
because a sibling check in the same preset still fires. That is not
hypothetical — it was reproduced twice while reviewing 0109.

## Fix

1. **Assert the violation's identity, not the process's exit.** Every
   preset-driven fixture should obtain `ArchViolation[]` (via
   `report: 'return'`, or off `ArchRuleError.violations` where the preset returns
   `void`) and require a violation whose `ruleId` matches the gate's name — the
   pattern `bad-adr.mjs` and `bad-crossval.mjs` now use. Then let `gateNode`
   assert the `ruleNote` it already prints, so the two cannot drift.
2. **Make `sh()` return `stdout` and `stderr` separately** so the JSON gates can
   `JSON.parse(r.stdout)` and assert one record with both the file and the
   ruleId, instead of substring-matching a merged blob.
3. **Give `scripts/check-baseline.mjs` a `--format` passthrough**, and switch
   `gateBaseline` and `gateInternalArch` to ruleId assertions. That collapses
   three assertion styles into one.
4. **Assert the fixture's own denominator.** `bad-gherkin-ts` is green when its
   feature set loads zero features: every citation dangles, so the fixture proves
   "some citation is dangling", which is trivially true on an empty set. It must
   assert the feature side loaded N > 0 — the same non-vacuity discipline the
   harness applies to everything else, applied inside a fixture.
5. **Guard the gate list itself.** `check:integrity`, `check:ledger`,
   `check:examples` and `check:docs-code` run in `validate` and have no
   non-vacuity row; nothing detects the omission, so deleting a row is a silent,
   green change. A check that every `check:*` script has a gate or an explicit
   waiver closes the same class one level up.

No changeset — `scripts/` is not a published package.
