# Bug 0134: `explain --format agent` renders "no rules" as a valid block and exits 0 — the documented guard cannot see it, and the AGENTS.md block is overwritten

## Status

- **State:** Draft — read from the source and confirmed against the shipped test
  and the shipped recipe. No red test yet.
- **Severity:** Medium — filed knowing the argument for High. Nothing here passes
  over drift that is present, which is what keeps it out of the High row; but the
  consequence is the **silent destruction of an adopter's standing instructions**,
  in a recipe this repo publishes, in the step whose stated selling point is that
  those instructions "cannot drift from what CI enforces"
  (`docs/agent-integration.md:82-84`). It is the `explain` half of the same
  honesty gap as [0130](./0130-cli-summary-counts-the-invocation.md): a command
  reporting a shape that examined nothing as if it had examined something.
- **Origin:** self-found · enforcement review of
  [proposal 004](../proposals/004-corpus-content-explain.md), which proposed
  mirroring this contract into two more dialects
- **Reported:** 2026-08-13

## Symptom

`packages/ts/src/cli/commands/explain.ts:69-73`, when zero rule descriptions load:

```ts
if (descriptions.length === 0) {
  lines.push('_No rules found._', '', AGENT_END)
  process.stdout.write(lines.join('\n') + '\n')
  return
}
```

`lines` already holds `AGENT_START`, the `## Architecture Rules` heading, the
"enforced by CI / will block your PR" sentence, and the check-in-your-loop
preamble (`:56-67`). So the empty case emits a **well-formed, sentinel-wrapped,
~11-line block** and returns — no throw, no non-zero exit.

The repo's own recipe consumes it at `docs/agent-integration.md:91-93`:

```bash
npx eess-ts explain arch.rules.ts --format agent > /tmp/eess-agent-block.md
# Guard: a failed/empty explain must never wipe the existing block.
[ -s /tmp/eess-agent-block.md ] || { echo "explain produced no output — AGENTS.md untouched" >&2; exit 1; }
```

`-s` is true when the file has size greater than zero. The empty-rules block is
~11 lines. **The guard passes.** The `awk` at `:97-99` then replaces everything
between the sentinels in `AGENTS.md` with it, and the agent's standing
architecture instructions become the words "_No rules found._".

The guard's comment names two failure modes — "a failed/empty explain". It
catches the first (a thrown `explain` truncates the redirect target, `-s` fails)
and is blind to the second, which is the one that produces a valid-looking
replacement.

`packages/ts/tests/cli/explain-command.test.ts:237` ·
`it('emits the "No rules found" block wrapped in sentinels')` asserts this
behaviour, including `<!-- eess-ts:start -->` and `<!-- eess-ts:end -->` around
it (`:247-251`). The empty path is **ratified**, not accidental — so any fix has
to change a test that currently passes, not merely add one.

## Reproduction

A rule file that loads but exports no builders — `export default []`, or a file
restructured so it `.check()`s inline instead of exporting:

```bash
npx eess-ts explain arch.rules.ts --format agent; echo "exit=$?"
# <!-- eess-ts:start -->
# ## Architecture Rules (auto-generated by eess-ts)
# ...
# _No rules found._
# <!-- eess-ts:end -->
# exit=0
```

Then run `update-agents-block.sh` from `docs/agent-integration.md:87-104` against
an `AGENTS.md` that already holds a populated block: the guard passes, the `awk`
runs, and the populated block is replaced by the empty one.

## Root cause

Two halves, and both must move.

1. **`explain` treats "zero rules" as a representable output rather than a
   fault.** It is the only reader in the CLI that does. `packages/ts/src/cli/load-rules.ts:49-54`
   states the opposite philosophy at the adjacent seam — _"a silently-dropped
   rule is a green-but-empty gate, which the whole point of this tool is to
   forbid"_ — and enforces it at the **shape** level (`:55-65`, `:90-98` throw
   loudly on a non-builder or a non-array). It does not enforce it at the
   **cardinality** level, and `explain` sits precisely on that hole.
2. **The recipe's guard tests the wrong property** — that the file has bytes,
   not that it describes any rules. No output shape currently lets it test the
   right one: `explain` writes nothing to stderr, prints no denominator, and
   returns the same exit code either way.

The two dialects also disagree about the empty case, so there is no single
contract to appeal to. `packages/mermaid/src/cli/commands/explain.ts:36-41` has
**no** empty branch at all: `formatMarkdown([])` emits a table header with zero
rows, and the JSON path (`:32`) emits `{"rules": []}`. Both exit 0.

## Why it matters

This is in the published `eess-ts` CLI and in a recipe this repo publishes as
executed-before-written (`docs/agent-integration.md:6-7`), so it reaches
adopters, and it is worst exactly where it is least visible: the block is
replaced with something that _looks_ deliberately generated, under sentinels
that assert provenance. The next agent to read `AGENTS.md` is told, in eess's
own voice, that the project enforces no architecture rules.

It is also the contract [proposal 004](../proposals/004-corpus-content-explain.md)
proposed mirroring into `eess-md` and `eess-gherkin`. Cloning it first would have
tripled the blast radius; the proposal was declined for other reasons, but this
is why the empty case has to be settled before any dialect copies it.

The vacuity harness cannot currently see any of this: `gateNode`
(`scripts/check-nonvacuity.mjs:252-286`) requires `exit 1`, and `gateCoverage`
(`:430-452`) enumerates only `check:*` package scripts, so a CLI subcommand is
invisible to it. `eess-ts explain` and `eess-mermaid explain` both sit in that
blind spot today.

## Fix

1. **Make the empty case loud in `eess-ts`.** Zero descriptions is a fault:
   non-zero exit with a stderr message naming what was read (rule files) and what
   was found (zero builders), with an explicit `--allow-empty` for the caller who
   genuinely wants the empty block. That preserves the sentinel-wrapped-empty
   output as an opt-in rather than deleting it.
2. **Rewrite the ratifying test**, not just add one — `explain-command.test.ts:237`
   asserts the current behaviour and will go red. Its replacement should assert
   the new default (non-zero, stderr names the count) plus the `--allow-empty`
   path still emitting the sentinel-wrapped block.
3. **Align `eess-mermaid`.** `formatMarkdown([])` emitting a header-only table and
   `{"rules": []}` at `:32` are the same defect without the sentinel consequence.
   Same rule, same flag.
4. **Fix the recipe's guard** at `docs/agent-integration.md:93` to test the
   property it means. Once (1) lands, `set -e` plus the non-zero exit does it and
   the `-s` test can stay as a belt-and-braces second check — but the comment must
   stop claiming a guarantee the `-s` line alone never gave.
5. **Record the harness hole**: a stated `NO_GATE_NEEDED` waiver (or equivalent)
   for CLI subcommands in `scripts/check-nonvacuity.mjs`, so "explain is
   uncovered" is written down rather than rediscovered.
